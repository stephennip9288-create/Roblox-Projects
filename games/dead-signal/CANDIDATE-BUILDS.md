# Dead Signal — cloud candidate builds (no Roblox publishing)

## Milestone

The read-only [Build Dead Signal Candidates (No Publish)](https://github.com/stephennip9288-create/Roblox-Projects/actions/workflows/dead-signal-candidates.yml) GitHub workflow now takes the four known-working complete staging `.rbxl` place files plus the editable Codex source in `games/dead-signal/dev/Source/Runtime/`, and generates **four candidate `.rbxl` files as downloadable GitHub Actions artifacts**.

This workflow never contacts Roblox Open Cloud, reads no `ROBLOX_API_KEY` secret, does not change `games/dead-signal/places/`, and does not modify the `Publish Roblox Place` workflow. It runs automatically on dev code PRs or can be manually invoked using the Actions UI.

## Inputs

- Full world/asset baseline: `games/dead-signal/places/{dispatch,blackwater,cinderworks,whiteout}/staging.rbxl`. These are the previously tested staging places, **not** the original v1.8.0 Work binary places.
- Editable code: `games/dead-signal/dev/Source/Runtime/{client,server,shared}/`.
- Staging Place IDs: generated by `python scripts/generate_dead_signal_place_configs.py` from the four active `deploy.json` manifests. Live production IDs are rejected in staging-generated PlaceConfig.
- Lune 0.11.0 installed by pinned `rokit.toml`.

## What the builder does

1. Reopens all four complete staging place baselines using Lune's Roblox serializer.
2. Captures the *non-script* instance hierarchy and key visual/physical properties (part sizes/CFrames/materials/colors, visible collision properties, mesh IDs, selected texture asset IDs, MaterialVariant maps).
3. Overlays the 60 editable Lua runtime scripts in the correct ReplicatedStorage, ServerScriptService and StarterPlayer service folders. Preserves `Config.ProfileStore`.
4. Replaces the staging PlaceConfig with a generated environment-specific module **for that particular place**, and rejects any production Place ID in it.
5. Serializes and reopens the full candidate place, confirms the script sources match, and requires the non-script inventory to match the baseline.
6. Runs Python artifact checks and archives `dispatch.rbxl`, `blackwater.rbxl`, `cinderworks.rbxl`, `whiteout.rbxl`, and `CANDIDATE-REPORT.json` as a 14-day GitHub Actions artifact.

**This is source overlay, not a map/art overhaul.** Any source-driven dynamic map generation in runtime will only run when Roblox starts a play session; an offline candidate parity audit doesn't prove the new geometry or enemy behavior in an actual engine session.

## Critical limitations — these candidates are not deployment-ready

- Lune serialization can omit or reinterpret Roblox properties it doesn't support, even if instance hierarchy and the selected checked properties match. **Terrain voxel data, unsupported asset properties, custom/engine-only data and full material fidelity are NOT certified.** Never treat the inventory check as exact byte-level or engine fidelity.
- Roblox Studio preview/gameplay, physical NPC collisions, navmesh/physics/pathfinding, mobile ADS/fire controls, teleport flow, private multiplayer admission, assets licensing and graphics/performance still require actual Studio and published-client acceptance testing.
- The existing staging binary files are the working rollback baseline. **Do not replace them with these artifacts until each candidate has passed stronger property/asset audit and explicit staged testing authorization.**
- The builder currently targets **staging only**. Production remains frozen behind the original manual approval workflow. Do not enable automatic promotion.
- Current working source is v1.8.0 development candidate. Some design directions and later backlog items remain unimplemented; an offline candidate build is not proof of feature completion.
- The included upstream `dev/Tools/build-places.luau` is not used here; it depends on a separate excluded rollback v1.7.0 kit.

## How to inspect candidates

Open [GitHub Actions](https://github.com/stephennip9288-create/Roblox-Projects/actions/workflows/dead-signal-candidates.yml), select the successful run and download **dead-signal-candidate-staging-...** under Artifacts. The report records per-place checks and explicitly marks `engineValidated=false`, `playable=false`, `safeToPublish=false`. You can compare candidates to the original staging files offline or open them in Roblox Studio as separate local files. Do not publish over the active places as part of this milestone.

## Next: stronger preservation verification

Before any Roblox staging deployment of source-built candidates:
1. Audit Terrain voxel content, all asset IDs and instances/properties omitted by the offline serializer, and compare with baseline Studio exports.
2. Open each candidate in Studio and visually inspect world, assets, lighting, UI and custom meshes/materials.
3. Perform controlled staging-only multiplayer and mobile test with explicit consent and rollback ready.
4. Only then consider a staging-only optional promotion workflow with a separate explicit approval and additional validation. Production remains separate.
